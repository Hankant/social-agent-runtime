# 工程接入与执行一致性检查

## 先找到已有框架的接入点

目标是支援现有实现，不为用户重新定义人群或建立行为模型。下表只检查数据与执行合同；没有约定的研究规则交还目标项目明确，不能静默推断。

| 层 | 核查内容 | 常见混淆 |
|---|---|---|
| 任务身份 | 唯一ID、轮次/事件、模型版本与输入hash | 缓存串用、请求记录归错用户 |
| 环境/状态 | 谁持有状态、哪个阶段可写、更新先后约定 | 并发任务提前读到别人的新行动 |
| 观察 | 冻结范围、序列化、边界和实际请求内容 | 源观察与发送内容不同或跨用户泄露 |
| 记忆 | 写入、选择、到期、注入与恢复是否符合既定合同 | 磁盘有记录但prompt未带入，恢复丢失历史 |
| 决策 | 请求输入输出、模型参数、校验及失败策略 | 重试换输入或伪造默认结果 |
| 执行 | 解析、合法性、子行动、幂等和提交 | 一个子行动重复导致合法结果一并丢失 |
| 输出 | 记录完整、计数一致、缺失和错误状态不混用 | 部分轮次被标完整，导出失败覆盖原异常 |

每项给出代码/配置/日志出处，区分“设计声称”“代码实现”“实际运行”。不凭正常曲线宣称实现正确。

## 接口和数据所有权

为目标框架映射 `reset → observe → decide → validate → apply → checkpoint`；名称无需一致。确定唯一写入者，列出线程共享对象：预算、缓存、request编号、连接池、门控、随机数、状态、日志句柄。检查看似局部的SDK客户端、线程上下文是否串用。

同步模型：冻结轮初状态；并发阶段只生成独立决策；全部任务有合法结果或合同允许的明确失败结果后，按稳定顺序统一应用；新内容下一轮可见。稳定顺序只保证提交顺序，不保证随机LLM响应相同。

异步模型：写明事件排序、时间语义和竞争处理，不随意改为轮次屏障。验证相同事件/缓存重放是否恢复一致状态。

## 工程验收的边界

使用固定假响应或已保存结果重放，检查串行/并发在目标合同下的状态与指标一致性、写入幂等、恢复完整性及预算守恒。随机LLM真实运行不要求逐字相同，也不能将其差异都归咎于工程错误。

若发现优化会改变阅读范围、历史长度、失败下线或状态顺序，指出变化并遵守用户授权；不在工程修复中偷偷引入。无法判断时保留现状并说明缺失约定。

研究假设、理论支持、经验校准、因果解释不属于本skill的验收目标。工程检查只说明执行是否符合约定、故障是否可恢复和性能是否改善；若用户另提研究问题，作为独立任务处理。
