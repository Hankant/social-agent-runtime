# 离线验证、故障定位与吞吐测量

如需加入合成数据或独立评价器，先读[验证器接入合同](validator.md)。本页负责运行故障与性能；生成机制、负对照、真值隔离和证据层次按该合同记录。

## 定位顺序

先读原始异常及请求记录，不拿 `Run interrupted(RuntimeError)` 包装层当根因。用run/parent链、配置hash、代码版本、进程启动身份、日志时间、完整检查点确认正在看哪次运行。只在授权范围内检查进程，不提取其环境凭据。

分解每轮时间：观察准备、排队、全局冷却、连接池等待、请求耗时、校验/再生成、持久化、轮末屏障与导出。排队和请求可能重叠，不把每项耗时简单相加当wall time。报告派发数、实际在途数、成功决策/min、错误与重试率、p50/p95、最后慢任务拖延，保留分母。

并发实验在相同工作量、prompt长度、模型、缓存、时间窗口和限流条件下比较。冷启动拒绝可能是RPM/TPM、共享账户、SDK重试或服务端过载，不从429/529单码断言。必要时查供应商当前官方文档，错误body只取安全字段。

## token专项

统计实际发送文本而非磁盘模板或base_prompt；记录输入结构占比：规则、persona、当前正文/评论、历史记忆、输出协议。记录每轮首次尝试与额外重试的供应商usage、缓存token、输出和usage未知请求。计数本地tokenizer时明确代理估算。

大批用户每轮重读大量评论会重复消耗；一个请求内部去重不等于跨请求免费。记忆缩短、评论抽样、输出字段删减会有不同的研究含义：原样序列化精简、审计不随请求发送通常是工程优化；修改输入内容、提示词或决策协议可能影响行为，需版本记录。调高并发不能直接降低总token。

输出上限过低可能截断重试；过高不代表真的生成那么多。检查长回复是否来自额外条件说明、无意开启推理或重复白名单。自述理由不证明各属性真实参与决策，不强制所有题目输出大量解释。

## 故障矩阵：在目标项目补齐，而不是只跑基础模块测试

| 场景 | 应观察的证据 |
|---|---|
| 1/N并发，固定假API结果 | 完整状态/指标一致，提交顺序固定，输入未被污染 |
| 慢首项、快后项 | 队列持续补位，在途不超过上限 |
| 并行额度争抢 | 请求编号唯一，预算不会因竞态超额派发 |
| 一波429，多轮拥堵，再稳定成功 | 全局事件聚合、有限退避、遵守Retry-After、恢复递增，无无限循环 |
| 坏JSON→成功 / 持续坏JSON | 尝试和原答保留，耗尽跨续跑继承，无虚构结果 |
| 鉴权/明确额度/磁盘故障 | 全局暂停，不把个体技术下线计数增加 |
| 已发请求断网、SIGINT或进程被杀 | 已保存成功复用，未决保留，不自动免费重发 |
| 保存响应后、提交轮次前崩溃 | 用缓存重放得到一致状态，不重复收费生成有效决策 |
| 原子提交后、导出前崩溃 | 断点仍有效，可重新导出，原始故障不被覆盖 |
| 损坏断点或hash不符 | 拒绝无记录恢复，不读半轮为完整轮 |
| 重复动作、部分无效子行动 | 符合项目合同的幂等/部分提交；不丢合法子结果 |
| 重启门控/缓存/预算、改配置或代码 | 状态继承，身份隔离；不偷换研究版本 |
| 全员、部分人、无人活跃 | 每轮人口ID/分母和缺失状态完整可解释 |

使用fake client、临时目录、固定随机源和可注入时钟。不要让测试依赖真实网络、密钥、套餐余额或长时间sleep。随机LLM无法承诺串行并发生成逐字相同；固定响应/重放测试验证的是工程语义。

## 规范化离线用量汇总

`scripts/summarize_events.py` 接收JSONL，每行是一个物理请求尝试的最终记录，不是事件流。一个请求的start/end/validation事件先由目标项目适配为一行。不得把所有审计目录盲扫为一次实验；限定明确的父子链并去重。

必填：`run_id`、`attempt_id`（run内唯一）、`decision_key`（同一逻辑任务跨重试和恢复保持一致）、`start_s`、`end_s`（统一时间原点的有限秒数）、`status`。

status：`validated`、`format_error`、`rate_limited`、`transport_error`、`unknown`、`cache_hit`、`global_error`、`agent_failed`。unknown表示结果未确认，不只是usage未返回。可选`input_tokens`/`output_tokens`是供应商返回非负整数，缺失为null。cache_hit为本地重放，不能把原响应usage作为本次新增用量；工具忽略该行用量。提供商缓存命中仍属实际API调用，应按真实校验状态记录，而非cache_hit。

示例：

```json
{"run_id":"run-a","attempt_id":"req-1","decision_key":"cfg-model-protocol-observation-agent-round-hash","start_s":0,"end_s":2,"status":"validated","input_tokens":100,"output_tokens":20}
```

工具只输出已知usage之和、未知usage记录数、不同逻辑决策完成数、观察窗口吞吐和请求延迟，不估算货币费用，不证明每轮完整性。用量未知不是零；HTTP失败可能也未提供usage。负数/重复请求/未知状态直接拒绝。

## 验收结果表达

基础模块离线通过、目标项目故障矩阵通过、小规模真实运行通过、完整正式实验完成四者分别报告。完整实验验收看目标轮次完整断点、hash、每轮唯一ID、状态/动作/指标关系、预算及未决请求。没有用户授权的连续监控工具或真实启动记录，就不能承诺后台一直监控。
